# M7: 信頼性・バックアップ・第1フェーズ判定

完了日: 2026-11-06 / ブランチ: `codex/backup-reliability`（M6から派生）

## 実装

- SQLite Online Backup APIを使い、バックアップDBに含まれるメタデータから添付一覧を取得して本体をコピーする。SQLite本体だけの単純コピーやWALを無視したコピーはしない。
- SQLite整合性・外部キー・添付サイズを確認し、SHA-256付きmanifestを作成する。ファイルとディレクトリを同期してから確定ディレクトリへrenameし、失敗時には過去の正常世代を残す。
- `dev` / `start` 起動時と毎分に当日のバックアップを確認する。停止中は次の起動で補う。直近7日と週次4世代を、重複を共用して保持する。複数プロセスの同時実行をロックし、死亡したプロセスのロックは回収する。
- 復元は新しい空の保存先のみ受け付ける。ハッシュ、サイズ、必要な添付、SQLite整合性を確認し、不正なパスとシンボリックリンクを拒否する。
- 保存容量・添付不整合・最新バックアップの画面、エラー境界、読み込み表示、壊れたブラウザ下書きの元データ救出を追加した。エラー境界はNext.js同梱ガイドの `retry` APIに従う。
- Node.js 24確認付き起動スクリプトと、再起動後の起動・復元手順をREADMEに追加した。実行環境のNode.jsは一時ディレクトリから `~/.local/share/labnote/node24` に移した。

## 検証結果

- 型チェック、本番ビルド、単体・統合28件、Chromium E2E 13件を通過。
- `npm ci` からの再インストールでも検証した。再導入後のTurbopack開発キャッシュで繰り返しリロードが起きたため、停止後に検証用 `.next-e2e` を再生成し、13件すべてを再確認した。本番ビルド・本番HTTPには発生していない。
- バックアップから空の別保存先に復元し、同じ記録・写真・プロトコル使用版・試料参照を本番HTTPで再表示した。
- 本番サーバーを停止・再起動して同じ本文を取得した。PC自体の再起動は実施していない。
- 破損したバックアップ、既存データへの復元、添付欠損時のバックアップ失敗、世代の選択を検証した。
- エディタの予期しない障害をエラー境界で表示し、壊れたlocalStorage下書きを無言で削除しないことをE2Eで検証した。

## 残課題・保留事項

- 実際のPC再起動、実際の研究での使い勝手・外観の最終承認は利用者のチェックリストで確認する。
- 大きなレイアウト変更、タグ・リンク欄を右パネルへ整理するなどの外観調整は保留。既存の緑と白のPC画面を基本にした。
- バックアップは同一PC内。物理故障対策の別媒体への保管は手動。未送信のブラウザ下書きは含まない。
- アプリ停止中には日次処理を実行せず、起動時に補完する。常時稼働・OSの自動起動設定は今回の対象外。
- 旧版の本文と使用時スナップショットはプレーンテキストで閲覧する。旧版専用のリッチ表示は保留。
- LAN・スマートフォン・認証・クラウド等の第2フェーズ機能は追加していない。

参照: [better-sqlite3 Backup API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#backupdestination-options---promise)。
